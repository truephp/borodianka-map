# Borodianka Map

Навчальний GIS-прототип на Leaflet з подвійними кольоровими лініями вулиць і будівлями Бородянки.

## Публікація
- GitHub → Settings → Pages → Source: **GitHub Actions**.
- GitHub → Actions → **Import OSM data** → **Run workflow** (гілка main). Імпортер намагається отримати валідовану межу населеного пункту (OSM relation 18281347), вулиці та контури будівель.
- Успішний імпорт створить `data/boundary.geojson`, `data/roads.geojson`, `data/buildings.geojson`. Після цього **Deploy site** запускається автоматично.
- Поки імпорт не виконався, наявний `roads.geojson` працює як раніше, а маска/будинки не показуються.

## Відображення
- Колір двох ниток уздовж доріг зараз **демонстраційний**, він не показує стан електропостачання.
- Будівлі (нейтральні) з'являються при zoom 16+; клік відкриває атрибути OSM, якщо є адреса.
- За наявності межі фон поза Бородянкою маскується. Обрізання полігонів на межі наразі приблизне: будівлі відбираються за геометричним центром, дороги — за вершинами всередині межі.
- Для продуктивності геометрію зберігаємо локально, а не запитуємо Overpass із браузера.

## Обмеження
- OSM relation 18281347 потребує підтвердження при імпорті. Якщо Nominatim або Overpass недоступні, workflow завершиться помилкою й наявні файли залишаться незмінними.
- Дорожні сегменти поки не зіставлені з будинками, дві лінії — не реальні електромережі.
- Залишилися питання коректного геометричного offset на поворотах та перехрестях.
- Не публікуємо реальних статусів ДТЕК на цьому етапі.

## Порівняння Visicom / OSM

У налаштуваннях виберіть підкладку **Visicom** та ввімкніть **Порівнювати контури OSM з підкладкою Visicom**. OSM-полігони показуються бірюзовими контурами поверх Visicom Tiles (без завантаження нової геометрії). Visicom може вимагати авторизацію через Referer або API-ключ. Ключі Data API не додавати до публічних файлів. Для Visicom Tiles потрібен ключ, обмежений за доменом, або погоджений доступ за Referer. Порівняння наразі візуальне: чисельність додаткових будинків Visicom автоматично не визначається.

## Локальна діагностика відповідностей Visicom ↔ OSM

У налаштуваннях увімкніть **Діагностика будівель**. Натисніть полігон OSM: у панелі видно його ID та адресу. Для порівняння з Visicom можна обрати локальний JSON через **Приватний JSON зіставлень Visicom**. Завантажений файл читається в пам'яті браузера: сайт не надсилає його на сервер і не зберігає в репозиторії.

Формат файлу (наведені нижче дані — лише вигаданий приклад структури):

```json
[
  {
    "osmId": 12345678,
    "candidates": [
      {"street": "Прикладна", "name": "12", "dist_meters": 5},
      {"street": "Прикладна", "name": "14", "dist_meters": 18}
    ]
  }
]
```

В інструменті показуються точні збіги адрес із OSM, кандидати для перевірки та конфлікти (та сама адреса в інших завантажених записах). Сама відстань не є підтвердженням прив'язки. Тестова GitHub Action наразі **не експортує** такого файлу — JSON потрібно підготувати локально з даних, на які є право використання. Наступний етап — погоджений захищений спосіб експорту результатів Visicom для зіставлення. Не публікуйте дані Visicom та API-ключ у репозиторії.

## Зашифрований експорт результатів Visicom

1. У `Settings → Secrets and variables → Actions` створіть окремий секрет `VISICOM_EXPORT_PASSWORD` (щонайменше 12 символів). **Не використовуйте API-ключ як пароль експорту.**
2. Запустіть workflow **Test Visicom Data API**. Він читає `VISICOM_API_KEY`, робить тестові запити, а результати шифрує AES-256-GCM з PBKDF2-SHA256 до завантаження artifact. У GitHub завантажується **лише зашифрований** файл `visicom-matches.enc.json`; строк зберігання artifact — 1 день.
3. У завершеному GitHub Actions run завантажте artifact `visicom-private-comparison` (ZIP), розпакуйте його.
4. На карті ввімкніть «Діагностика будівель», у полі «Пароль експорту» введіть `VISICOM_EXPORT_PASSWORD` та виберіть `visicom-matches.enc.json`. Файл розшифровується у вашому браузері; пароль і розшифровані дані не надсилаються на сервер.

**Увага:** artifacts публічного GitHub-репозиторію не слід вважати приватними. Шифрування обов'язкове, незалежно від терміну зберігання. Репозиторій і Pages не містять даних Visicom. Публікувати розшифрований JSON не можна без перевірки прав використання.

## Тест Visicom Feature Polygon

Workflow **Test Visicom Feature Geometry** отримує до 30 адресних features, повертає лише унікальні Polygon/MultiPolygon, шифрує у `visicom-polygons.enc.json` паролем `VISICOM_EXPORT_PASSWORD` та завантажує одноденний artifact `visicom-feature-polygons`. Файл не входить до Pages чи git. Завантажте ZIP, розпакуйте, на карті відкрийте налаштування, введіть пароль експорту та виберіть зашифрований JSON у тому самому полі імпорту. Перемикач «Показувати полігони Visicom» керує фіолетовими полігонами, popup містить адресу й Visicom ID. Це перевірка геометрії адресних features; її відповідність фізичним контурам будівель ще потрібно оцінити візуально. Ліцензія Visicom може обмежувати зберігання та повторне використання геометрії.

## Пілот просторового імпорту Visicom (незалежно від OSM)

Workflow `Test Visicom Spatial Discovery` використовує збережену межу Бородянки, шукає `adr_address` через `intersect` з WKT-прямокутником та підділяє насичені ділянки (250 об'єктів). Наразі це **обмежений пілот**: максимум чотири комірки та тридцять Feature-полігонів, не повний імпорт міста. В логах `DISCOVERY` є прапорець `complete`: лише він разом із нульовою чергою й відсутністю помилок дозволяє говорити про повноту. При успіху workflow створює лише зашифрований artifact `visicom-spatial-pilot` (1 день), файл `visicom-spatial.enc.json`. Він сумісний із локальним імпортом полігонів на карті, якщо ввести `VISICOM_EXPORT_PASSWORD`. Геометрія Visicom не комітиться та не публікується на Pages. Перевірка IoU та остаточна класифікація OSM-only/Visicom-only ще не реалізовані.

## Масштабований імпорт Visicom (два workflow)

1. **Test Visicom Spatial Discovery** (`.github/workflows/visicom-spatial.yml`) сканує bounding box Бородянки, рекурсивно ділить комірки з 250 результатами. До 1500 комірок, лог `DISCOVERY`. Повнота означає порожню чергу, 0 помилок і 0 нерозділених насичених комірок. Експортує **лише зашифрований** `visicom-address-index.enc.json` у artifact `visicom-address-index` (1 день). Якщо сканування неповне, job завершується помилкою: такий індекс не приймається наступним етапом.
2. **Visicom Feature Batch** (`.github/workflows/visicom-feature-batch.yml`) вручну приймає `discovery_run_id` попереднього успішного запуску, `offset` (0, 100, 200...) і `batch_size` (типово 100). Завантажує зашифрований index через GitHub Actions, розшифровує тільки на runner, викликає Feature API й шифрує окремий batch `polygons.enc.json` у artifact `visicom-polygon-batch`. Щоб продовжити імпорт після перерви, запустіть наступний batch із новим offset; попередні запити не повторюються. За помилок запитів workflow помічається failed і batch потребує перевірки.
3. На карті можна завантажити один зашифрований batch через існуючий локальний імпортер полігонів. Об'єднання кількох batch у браузері, IoU та класифікація OSM-only/Visicom-only — **ще не реалізовані**.

**Обмеження:** пошук наразі охоплює bounding box, а не лише точки всередині адміністративного полігона. Частина результатів може належати прилеглим територіям. Критерій `completeDiscovery` гарантує лише, що не залишилось невирішених комірок запитаного прямокутника, а не повноту всіх будівель у Visicom. Доступ і зберігання геометрії регулюються ліцензією Visicom. У GitHub Pages ці дані не завантажуються.

## Накопичення batch та геометричне зіставлення

У карті можна **послідовно** завантажувати декілька `polygons.enc.json` (із різних Visicom Feature Batch). Після локального розшифрування полігони додаються в пам'ять браузера за унікальним `visicomId` (повторні ID перезаписуються); раніше завантажені не зникають. «Очистити полігони Visicom» звільняє цю локальну колекцію. Після перезавантаження сторінки дані не зберігаються.

Перемикач «Порівняти геометрію OSM / Visicom» обчислює IoU (площу перетину / площу об'єднання) для полігонів із перетином bounding box. Поріг 0,65: зелений = збіг, фіолетовий = Visicom без збігу в OSM, блакитний = OSM без збігу серед **завантаженої вибірки**. Поки не завантажено всі порції Visicom, статус «тільки OSM» не можна вважати підтвердженим. У наведеній статистиці деякі багаточастинні/складні геометрії можуть не пройти автоматичну перевірку й потребують ручної оцінки. Обчислення відбувається тільки в браузері: незашифровані полігони не надсилаються на сервер.

## Повний імпорт Visicom одним запуском

Workflow **Visicom Full Feature Export** (`.github/workflows/visicom-full-features.yml`) приймає `discovery_run_id` завершеного індексу адрес (наприклад, `41505103037`, поки його artifact не прострочений). Він отримує усі Feature API об'єкти з індексу, по одному з паузою 400 мс та до чотирьох спроб при збої. Після кожних 100 нових запитів створюється **зашифрований локальний checkpoint**, а в кінці — **один зашифрований** `visicom-buildings.enc.json` у artifact `visicom-buildings` (1 день). Окремий artifact `visicom-feature-checkpoint` містить зашифрований прогрес для відновлення і не є базою для карти.

Для відновлення вкажіть `resume_run_id` попереднього запуску Full Feature Export; дані з checkpoint об'єднуються, вже виконані ID пропускаються, невдалі пробуються повторно. Обидва artifact мають обмежений строк зберігання, тому для продовження потрібні ще доступні індекс і checkpoint. Якщо якийсь запит остаточно не вдався, workflow повідомить про неповноту, але зашифрований файл і checkpoint все одно будуть доступні. У браузері відкрийте `visicom-buildings.enc.json` як звичайний зашифрований полігональний експорт. **Зберігання та використання геометрії Visicom мають відповідати їхній ліцензії.**

## Розширене геометричне зіставлення

У згортаній секції «Діагностика» доступні регульовані пороги IoU (впевнений, ймовірний і слабкий) та перекриття меншого полігона. За замовчуванням: IoU ≥ 0.65 — зелений, 0.30–0.65 — жовтий, 0.10–0.30 — помаранчевий, нижче 0.10 — фіолетовий для Visicom і блакитний для OSM. Якщо площа перетину / площа меншого полігона ≥ 0.80, збіг вважається **ймовірним**, не впевненим. Дані Visicom за замовчуванням фільтруються за перетином з адміністративним контуром Бородянки, але полігон на межі може частково виходити за територію. Перерахунок локальний і не робить нових API-запитів.

## Діагностика конфліктів геометрії

У секції «Діагностика» після завантаження зашифрованих Visicom-полігонів увімкніть «Виділити конфлікти зіставлення». Червоні контури показують випадки, коли один Visicom-полігон має кілька OSM-кандидатів зі статусом «ймовірний» або «впевнений», або навпаки. Статистика рахує обидва напрямки. У popup полігонів наведено ID відповідників, IoU та перекриття меншого полігона. Зміна порогів автоматично перераховує конфлікти. Це неоднозначні геометричні відповідності, а не доведені дублікати; ручні рішення не зберігаються.

## Єдиний шар будівель (експериментально)

Після завантаження зашифрованого `visicom-buildings.enc.json` в секції «Діагностика» доступний перемикач **Єдиний шар будівель**. Visicom-полігони мають пріоритет (фіолетові), решта OSM відображається блакитним. OSM-полігон приховується лише коли є **взаємно однозначна відповідність** (рівно один Visicom ↔ один OSM) та `IoU ≥ 0.65` незалежно від змінених діагностичних повзунків. Неоднозначні, часткові чи слабкі збіги залишаються в обох шарах, без автоматичного видалення. Вихідні GeoJSON не змінюються. Растрові тайли OSM усе ще можуть містити намальовані будівлі, їх не можна прибрати з PNG; це приховує лише наш векторний дубль. Visicom геометрія зберігається тільки в оперативній пам'яті браузера і не публікується.
